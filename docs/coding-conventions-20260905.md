# 코드 및 기술 규칙

> 팀원이 같은 기준으로 코드를 작성·검토하고, 변경 사항을 안전하게 통합하기 위한 규칙입니다.

**문서 상태:** 팀 합의 완료
**적용 범위:** GitHub 협업, 코드 스타일, 커밋, PR, 공통 기술 변경

## 1. 기본 원칙

- 모든 작업은 **브랜치 기반으로 진행**하며 `main` 및 `develop` 브랜치에 직접 push 하지 않습니다.
- 신규 작업은 **최신 `develop` 브랜치를 pull**한 뒤 시작합니다.
- 작업을 작은 기능·수정 단위로 나누고 **PR을 통해 코드 리뷰 후 병합**합니다.
- 작성자는 본인의 변경 사항과 확인 방법을 설명할 수 있어야 합니다.
- 공통 설정·의존성·DB·API 변경은 영향을 받는 팀원과 먼저 공유합니다.
- 기술적 의견이 다를 경우 **근거 기반으로 논의 후 결정**합니다.

## 2. Branch

### 브랜치 역할

| 브랜치         | 역할                 | 생성 기준        | PR 대상                     |
| ----------- | ------------------ | ------------ | ------------------------- |
| `main`      | 배포 가능한 안정 버전       | 초기 저장소 구성    | —                         |
| `develop`   | 개발 결과 통합 및 연동 확인   | `main`       | 배포 시 `main`               |
| `feature/*` | 기능 추가·개선           | 최신 `develop` | `develop`                 |
| `fix/*`     | 개발 중 발견한 오류 수정     | 최신 `develop` | `develop`                 |
| `chore/*`   | 설정·의존성·문서 등 유지 작업  | 최신 `develop` | `develop`                 |
| `hotfix/*`  | 현재 배포 버전의 긴급 오류 수정 | 최신 `main`    | `main`, 이후 `develop`에도 반영 |

### 브랜치 이름

```text
브랜치종류/이슈번호-도메인-작업내용
```

- 영문 소문자·숫자·하이픈을 사용합니다.
- 공백과 개인 이름 대신 작업 목적을 적습니다.
- 도메인은 `auth`, `housing`, `budget` 등 담당 기능 영역을 의미합니다.
- 공통 작업은 `common`, 문서 작업은 `docs` 등을 사용할 수 있습니다.

예시:

```text
feature/12-housing-create-form
fix/27-budget-total
chore/31-common-lint-config
chore/35-docs-local-setup
hotfix/42-auth-login-error
```

### 작업 시작·동기화

1. 신규 작업을 시작하기 전에 로컬 미커밋 변경 사항을 확인합니다.
2. 로컬 `develop`을 원격의 최신 상태로 갱신합니다.
3. 최신 `develop`에서 작업 브랜치를 만듭니다.
4. 기존 작업 브랜치를 계속 사용하는 경우, 필요한 시점에 최신 원격 `develop`을 작업 브랜치로 병합합니다.
5. 충돌이 발생하면 관련 코드 담당자와 변경 의도를 확인합니다.

공유 브랜치의 이력을 임의로 변경하거나 force push하지 않습니다. 충돌을 해결할 때 다른 사람의 변경을 일괄 삭제하지 않습니다.

### 병합 방식

- 작업 브랜치 → `develop`: **Create a merge commit**
- `develop` → `main`: **Create a merge commit**
- 긴급 수정: `main` 반영 후 수정 사항이 포함된 `main`을 `develop`에 PR로 병합해 동기화합니다.

작업 브랜치는 병합 후 삭제하지 않고 다음 작업에는 새 브랜치를 만듭니다. `main`과 `develop`은 유지합니다. 긴급 수정 브랜치에서 작업 후에는 양쪽 반영을 확인합니다.

## 3. Code Style

### 적용 도구

- **Prettier:** 들여쓰기·줄바꿈·따옴표 등 코드 형식 통일
- **ESLint:** JavaScript·TypeScript의 오류 가능성과 코드 규칙 검사
- 개인 편집기 설정보다 저장소에 공유된 설정을 우선합니다.
- ESLint와 Prettier의 형식 규칙이 충돌하지 않도록 구성합니다. [Prettier 공식 안내](https://prettier.io/docs/integrating-with-linters)

### 기본 스타일

| 항목         | 규칙                               |
| ---------- | -------------------------------- |
| 들여쓰기       | 공백 4칸                            |
| 세미콜론       | JavaScript·TypeScript에서 사용       |
| 문자열        | JavaScript·TypeScript에서 싱글 쿼트 우선 |
| 줄바꿈        | LF                               |
| 파일 끝       | 개행 유지                            |
| 사용하지 않는 코드 | 불필요한 변수·import·임시 코드 제거          |

JSON과 JSX 속성 등은 언어 문법과 포맷터 설정을 따릅니다. Java를 사용한다면 문자열에 더블 쿼트를 사용하며, Java용 포맷터와 검사 규칙을 별도로 정합니다.

### Prettier 설정안

```json
{
    "tabWidth": 4,
    "useTabs": false,
    "semi": true,
    "singleQuote": true,
    "endOfLine": "lf",
    "overrides": [
        {
            "files": ["*.yml", "*.yaml"],
            "options": {
                "tabWidth": 2
            }
        }
    ]
}
```

YAML은 공백 2칸을 사용하도록 예외를 둡니다. 그 외 지원 파일은 위 설정과 포맷터의 언어별 처리 결과를 따릅니다. [Prettier 옵션 문서](https://prettier.io/docs/options)

### 이름과 주석

- 변수·함수는 역할이 드러나는 이름을 사용합니다.
- JavaScript·TypeScript의 변수·함수는 `camelCase`를 기본으로 합니다.
- 클래스·타입·UI 컴포넌트는 해당 언어와 프레임워크의 관례를 따릅니다.
- `data1`, `temp2`처럼 의미가 불분명한 이름을 피합니다.
- 주석은 코드만으로 알기 어려운 이유·제약·계산 근거를 설명합니다.
- 해결하지 않은 TODO는 관련 이슈를 연결합니다.
- 의미 있는 운영 로그는 유지하되, 임시 디버깅 출력과 민감한 정보 출력은 제거합니다.

폴더 구조와 파일명 규칙은 기술 스택 선정 후 별도로 확정합니다.

## 4. Commit

### 형식

```text
type: 작업 내용
```

예시:

```text
feat: 주거 후보 입력 검증 추가
fix: 월별 지출 중복 합산 수정
docs: 로컬 실행 방법 작성
refactor: 생활비 계산 함수 분리
test: 수입 지연 시 잔액 계산 검증 추가
```

### 타입 목록

| 타입         | 설명                                   |   |
| ---------- | ------------------------------------ | - |
| `feat`     | 새로운 기능 및 화면, 사용자 동작 추가               |   |
| `fix`      | 잘못된 동작, 화면, 버그 수정                    |   |
| `docs`     | 코드 변경 없이 설명 문서만 수정                   |   |
| `style`    | 논리 및 동작 변화 없는 코드 형식 수정 (포맷팅, 세미콜론 등) |   |
| `refactor` | 논리 및 동작을 유지한 구조 개선                   |   |
| `test`     | 테스트 코드 추가·수정                         |   |
| `chore`    | 빌드·의존성·공통 설정 등 유지 작업                 |   |
| `comment`  | 필요한 주석 추가 및 변경                       |   |
| `!HOTFIX`  | 긴급한 버그 수정                            |   |

- 파일 수정이나 삭제 시 변경 목적에 맞춰 `refactor`, `chore` 등 사용
- UI 추가는 `feat`, 잘못된 UI 수정은 `fix`

### 작성 원칙

- 한 커밋에는 가능한 한 하나의 목적을 담습니다.
- ‘수정’, ‘작업 완료’ 대신 무엇을 바꿨는지 적습니다.
- 기능 변경과 전체 파일 포맷 변경을 한꺼번에 섞지 않습니다.
- 생성 파일·빌드 결과·비밀 정보가 포함되지 않았는지 확인합니다.

## 5. Pull Request

### PR 생성 기준

- 검토 가능한 기능·수정 단위가 되면 생성합니다.
- 설계나 방향에 대한 조기 의견이 필요하면 **Draft PR**을 사용합니다.
- 일반 작업의 대상 브랜치는 `develop`입니다.
- 하나의 PR에는 가능한 한 하나의 목적을 담습니다.
- PR 작성자는 먼저 변경 내용을 직접 확인합니다.

### PR 제목

```text
[타입] #이슈번호 작업 내용
```

예시:

```text
[feat] #12 주거 후보 등록 API 구현
[fix] #27 월별 지출 중복 합산 수정
```

### 이슈 연결·종료

일반 PR 본문에는 다음처럼 관련 이슈를 표시합니다.

```text
Refs #12
```

`#12`는 이슈 참조이며, 위 표기 자체로 이슈가 자동 종료되지는 않습니다.

**기본 브랜치가 아닌&#x20;****`develop`****&#x20;대상 PR에서는&#x20;****`Closes #12`****를 적어도 자동 종료되지 않습니다.** 개발 작업 이슈는 `develop` 병합과 완료 조건 확인 후 담당자가 종료합니다. 배포까지 필요한 작업은 해당 조건을 확인할 때까지 유지합니다. [GitHub 공식 안내](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

### PR 본문 템플릿

```markdown
## 관련 이슈
- Refs #이슈번호

## 변경 목적
<!-- 어떤 문제를 해결했는지 작성해주세요. -->
- 

## 작업 내용
<!-- 주요 변경 사항을 작성해주세요. -->
<!-- 예:
- Room 엔티티와 Participant 엔티티 간 1:N 관계 설정
- 방 생성 시 고유한 6자리 URL Slug 생성 로직 추가
- NestJS ValidationPipe를 이용한 입력값 검증 적용
-->

## 확인 방법 및 결과
<!--
- 실행한 검사·테스트와 결과를 작성합니다.
- API 테스트 시 응답 결과(Postman/Swagger)나 실행 결과 스크린샷을 첨부합니다.
- 화면 변경은 필요한 스크린샷을 첨부합니다.
- 수동 확인은 재현 순서, 기대 결과, 실제 결과를 적습니다.
- 확인하지 못한 항목이 있으면 이유를 적습니다.
-->

## 리뷰 포인트
<!-- 리뷰어가 집중해서 봐주었으면 하는 부분이 있다면 작성해주세요. -->
<!-- 예:
- 슬러그 생성 알고리즘이 중복을 충분히 방지할 수 있을까요?
- Prisma 트랜잭션 처리가 적절하게 되었는지 확인 부탁드립니다.
-->

## 영향 및 후속 작업
<!--
- API·DB·환경변수·의존성 변경 여부
- 다른 팀원이 수행해야 할 설정 또는 작업
- 남은 문제와 연결된 이슈
- 해당 사항이 없으면 ‘없음’으로 작성합니다.
-->

## 체크리스트
- [ ] 대상 브랜치와 변경 파일을 확인했습니다.
- [ ] 합의된 코드 스타일을 적용했습니다.
- [ ] 커밋 메시지 컨벤션을 준수했습니다.
- [ ] 변경에 필요한 검사·빌드·테스트를 수행하고 결과를 적었습니다.
- [ ] 임시 코드와 불필요한 디버깅 출력(console.log)을 정리했습니다.
- [ ] 비밀 정보가 포함되지 않았습니다.
- [ ] 필요한 문서와 실행 안내를 갱신했습니다.
```

## 6. PR 리뷰와 병합

### 승인 기준

- 작성자를 제외한 **최소 1명이 검토하고 승인**합니다.
- 필수 수정 의견과 변경 요청을 해결한 후 병합합니다.
- 의견을 반영하지 않을 경우 이유를 설명하고 합의합니다.
- 승인 이후 동작에 영향을 주는 변경을 추가하면 재검토를 요청합니다.
- 설정된 필수 자동 검사가 있다면 통과해야 합니다.

### 리뷰 의견 구분

| 표시     | 의미                             |
| ------ | ------------------------------ |
| `[필수]` | 병합 전에 해결해야 하는 오류·요구사항 누락       |
| `[제안]` | 개선 의견. 논의 후 현재 PR 또는 후속 작업에 반영 |
| `[질문]` | 구현 의도나 동작 확인                   |

취향 차이를 필수 수정으로 요구하지 않습니다. 코드 형식은 공통 도구로 처리하고, 리뷰에서는 동작·이해 가능성·예외 처리를 중심으로 확인합니다.

### 초보 팀원과의 리뷰

- 함께 실행하거나 작성자의 설명을 들으며 검토할 수 있습니다.
- 리뷰어는 직접 확인한 범위와 추가 확인이 필요한 부분을 남깁니다.
- 계산·인증·DB 변경처럼 영향이 큰 부분은 이해 가능한 담당자와 함께 검토합니다.
- 이해하지 못한 변경을 승인 조건 충족만을 위해 승인하지 않습니다.

### 병합 담당

조건을 충족한 일반 작업 PR은 작성자가 병합하는 것을 기본으로 합니다. 배포 PR은 지정한 배포 담당자가 확인 후 병합합니다.

검토가 지연되면 팀 채팅에서 요청하고 검토자를 조정합니다. 승인 없이 직접 push하는 방식으로 우회하지 않습니다.

### 저장소 설정 제안

`main`과 `develop`에는 다음을 설정합니다.

- PR을 통한 변경
- 최소 1명 승인
- force push·브랜치 삭제 제한
- 실제 구성된 자동 검사의 통과 요구

설정 지원 범위는 저장소 공개 여부와 GitHub 요금제에 따라 확인합니다. [GitHub 보호 브랜치 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 7. API·DB·공통 로직 변경

### API

- 구현 전에 요청·응답·오류 형식을 관련 담당자와 맞춥니다.
- 필드명·자료형·필수 여부·예시를 문서로 남깁니다.
- 기존 응답이나 필드를 변경하면 프런트엔드·백엔드 담당자에게 알립니다.
- 프런트엔드 검증과 별개로 서버에서도 입력을 검증합니다.
- 로딩·빈 결과·오류 상태의 화면 처리도 함께 정합니다.

### DB

- 공용 DB 구조를 개인이 임의로 수정하지 않습니다.
- 스키마 변경은 재현 가능한 변경 파일과 적용 방법을 함께 관리합니다.
- 기존 데이터에 미치는 영향과 초기 데이터 변경 여부를 PR에 적습니다.
- 공용·배포 DB의 데이터 삭제나 초기화는 사전에 합의합니다.
- 계정 기능을 구현한다면 본인 데이터만 접근·수정할 수 있는지 확인합니다.

### 계산·조건 판정

- 금액 단위, 소수점·반올림 방식, 날짜 기준을 문서화합니다.
- ‘미입력’, ‘알 수 없음’, `0`을 구분합니다.
- 정상값·경계값·중복 입력·누락 입력 등 중요한 사례를 검증합니다.
- 계산식을 여러 곳에 중복 구현할 경우 기준과 일치 확인 방법을 정합니다.
- 정책·공고에 따른 판단은 출처와 기준일을 기록합니다.

## 8. 실행 환경과 의존성

- 실행에 필요한 언어·런타임·패키지 매니저 버전을 공유합니다.
- 같은 프로젝트에서 여러 패키지 매니저를 혼용하지 않습니다.
- 사용하는 패키지 매니저의 잠금 파일을 저장소에 포함합니다.
- 새 라이브러리는 도입 목적·대안·영향을 PR에 적습니다.
- `.env`와 실제 키·비밀번호는 커밋하지 않습니다.
- 필요한 환경변수 이름은 값 없는 예시 파일로 공유합니다.
- README에는 설치·실행·검사·테스트·초기 데이터 준비 방법을 기록합니다.

검사 명령과 CI 구성은 기술 스택 확정 후 정합니다. 초기에는 포맷·린트·타입 검사·빌드와 핵심 로직 테스트 중 프로젝트에 해당하는 항목부터 구성합니다.
