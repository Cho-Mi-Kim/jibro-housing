# 캡스톤 프로젝트 팀 컨벤션

> 팀원 모두가 진행 상황을 이해하고, 맡은 일을 책임 있게 완성하며, 함께 배우기 위한 협업 기준입니다.

**문서 상태:** 팀 합의 전 초안
**적용 기간:** 이번 학기 캡스톤 프로젝트
**최종 수정일:** 2026.09.04
**프로젝트명 / 팀명:** 미정
**정기회의 시간:** 첫 회의에서 결정

이 문서의 회의 주기·연락 기준·개발 절차는 제안입니다. 팀 합의 후 확정하며, 실제 운영에 맞지 않는 규칙은 회의에서 수정합니다.

## 1. 우리가 지향하는 프로젝트

- 구체적인 사용자 문제와 근거를 바탕으로 기획합니다.
- 학기 안에 구현하고 검증할 수 있는 범위를 선택합니다.
- 각 팀원이 설명할 수 있는 결과물과 학습 경험을 남깁니다.
- 진행 상황과 어려움을 일찍 공유합니다.
- 팀원 간 실력 차이를 고려해 작업을 나누고, 특정인에게 일이 몰리지 않도록 조정합니다.

**모르는 것은 괜찮습니다. 막힌 사실을 공유하고 해결 과정에 참여하는 것을 중요하게 생각합니다.**

## 2. 역할과 책임

### 역할 분담 원칙

- 모든 작업에는 **주 담당자 1명**을 정합니다.
- 필요하면 도움을 주는 사람과 검토자를 별도로 정합니다.
- 담당자는 구현뿐 아니라 진행 공유·결과 확인·관련 기록까지 책임집니다.
- 도움을 받더라도 담당자가 결과를 이해하고 설명할 수 있어야 합니다.
- 역할은 고정하지 않고 작업량과 학습 상황에 따라 조정합니다.

| 역할        | 주요 책임                           |
| --------- | ------------------------------- |
| 팀 리더      | 일정·우선순위 조율, 회의 진행, 의사결정 정리      |
| 작업 담당자    | 작업 수행, 진행 공유, 문제 제기, 결과 확인      |
| 검토자       | 요구사항 충족 여부와 결과 확인, 개선 의견 전달     |
| 회의 기록 담당자 | 결정 사항·후속 작업·미결 사항 기록. 회의별 순환 가능 |

**리더는 모든 미완료 작업을 대신 수행하는 사람이 아닙니다.** 일정이 어려워지면 범위 축소·작업 분할·공동 작업·재배정 순으로 해결 방법을 논의합니다.

### 초보 팀원의 참여

- 처음에는 작고 결과가 명확한 작업부터 맡습니다.
- 개발 환경 설정과 기본 협업 방법은 함께 실습합니다.
- 문서와 발표도 필요한 기여로 인정하되, 관심과 수업 목표에 맞춰 작은 구현·테스트 경험을 확보합니다.
- 숙련자가 대신 완성하기보다 담당자가 수정하고 마무리할 수 있도록 돕습니다.

## 3. 소통과 기록

| 도구       | 용도                         |
| -------- | -------------------------- |
| 팀 단체 채팅방 | 빠른 질문, 일정 조율, 긴급 공유        |
| Notion   | 기획, 근거 자료, 회의록, 결정 사항, 일정  |
| GitHub   | 코드, 개발 작업, 변경 이력, 코드 검토    |
| 디자인 도구   | 화면 흐름과 UI 협업. 사용 도구는 추후 결정 |

### 기본 원칙

- 일정이나 작업에 영향을 주는 내용은 팀 전체가 확인할 수 있는 곳에 남깁니다.
- 개인 대화에서 결정된 사항도 관련 페이지나 작업에 기록합니다.
- 답변에 시간이 걸리면 확인 여부와 답변 가능한 시점을 먼저 알립니다.
- 채팅에서 논의한 최종 결정은 Notion 또는 해당 GitHub 작업에 옮깁니다.

### 연락 기준 제안

- 평일에는 원칙적으로 24시간 안에 확인 또는 답변합니다.
- 수업·시험·아르바이트 등으로 대응이 어려운 일정은 미리 공유합니다.
- 야간이나 주말의 즉각적인 응답을 기본으로 요구하지 않습니다.
- 팀 일정에 영향을 주는 긴급 사항에는 영향과 필요한 응답 시점을 함께 적습니다.

## 4. 회의 운영

### 정기회의 제안

- 주 1회, 30\~45분 진행합니다.
- 회의 전에 각자 작업 상태와 논의할 문제를 갱신합니다.
- 설명이나 디버깅이 길어지는 사안은 필요한 인원끼리 별도 시간을 잡습니다.

### 기본 안건

1. 지난주 결과물 확인
2. 막힌 작업과 일정 위험 공유
3. 교수님 피드백·사용자 조사 결과 검토
4. 이번 주 목표와 담당자 결정
5. 결정되지 않은 사항과 다음 확인 일정 정리

### 회의록 필수 항목

**일시 / 참석자 / 논의 내용 / 결정 사항 / 후속 작업·담당자·기한 / 미결 사항**

회의를 마칠 때 각 팀원이 **다음 회의까지 무엇을 완료해야 하는지** 확인합니다.

불참 시 가능한 한 사전에 알리고 진행 상황을 남깁니다. 이후 회의록을 확인하고 본인 작업에 영향을 주는 결정에 대해 필요한 의견을 전달합니다.

## 5. 작업 관리

### 작업을 만들 때 적을 내용

| 항목    | 내용                |
| ----- | ----------------- |
| 작업명   | 무엇을 완료할지 구체적으로 작성 |
| 목적    | 사용자 문제·요구사항과의 연결  |
| 담당자   | 주 담당자 1명          |
| 완료 조건 | 어떤 상태가 되면 완료인지    |
| 목표일   | 담당자와 협의한 일정       |
| 선행 작업 | 먼저 필요한 자료·설계·기능   |
| 검토자   | 결과를 확인할 사람        |
| 참고자료  | 관련 문서·화면·근거 링크    |

‘프런트엔드 개발’처럼 큰 작업은 화면이나 기능 단위로 나눕니다.

예: **‘주거 후보 입력 화면에서 필수값 검증과 저장 요청 처리하기’**

### 작업 상태

**할 일 → 진행 중 → 검토 요청 → 완료**

진행이 막힌 작업에는 상태와 별개로 **막힌 이유와 필요한 도움**을 표시합니다.

### 운영 원칙

- 처음에는 1인당 핵심 작업 1개를 진행하는 것을 기본으로 합니다.
- 작업량을 예측하기 어려우면 조사·실험부터 별도 작업으로 나눕니다.
- 일정은 담당자와 협의해 정하며, 처음 예상이 틀리면 근거를 남기고 조정합니다.
- 같은 작업의 자세한 진행 상태를 여러 도구에 중복 작성하지 않습니다. 개발 작업은 GitHub를 기준으로 관리하고 Notion에서 연결합니다.

## 6. 막혔거나 일정이 늦어질 때

### 질문할 때 함께 남길 내용

- 하려던 작업과 기대한 결과
- 실제로 발생한 현상
- 확인한 오류 메시지 또는 화면
- 이미 시도한 방법
- 필요한 도움과 다른 작업에 미치는 영향

혼자 같은 시도를 반복하고 있다면 진행 상황을 공유합니다. **30\~60분 정도 진전이 없는 경우를 초기 공유 기준으로 제안**하며, 시간 자체보다 막힌 내용을 설명하는 데 집중합니다.

### 일정 변경 절차

1. 지연 가능성을 알게 되면 담당자가 공유합니다.
2. 남은 작업과 예상 소요를 확인합니다.
3. 필수 범위 축소, 작업 분할, 도움 요청, 재배정을 논의합니다.
4. 변경된 담당자·완료 조건·목표일을 기록합니다.

야근이나 특정 팀원의 대체 작업을 기본 해결책으로 삼지 않습니다.

## 7. 기획·근거 자료 컨벤션

### 사실과 가설 구분

- **확인된 사실:** 공식 자료, 실제 인터뷰, 관찰 결과 등 근거가 있는 내용
- **문제 가설:** 아직 확인하지 않은 사용자 불편이나 행동
- **해결 가설:** 제안 기능이 문제를 개선할 것이라는 예상
- **팀 결정:** 조사와 제약을 고려해 선택한 방향

### 자료를 남길 때

**출처 / 작성·발표 시점 / 확인일 / 핵심 내용 / 프로젝트와의 관련성**을 기록합니다.

- 통계는 조사 대상·기간·범위를 확인합니다.
- 인터뷰 몇 건을 전체 타깃의 의견으로 확대하지 않습니다.
- 사용자의 말과 팀의 해석을 구분합니다.
- 반대 사례와 기존 서비스로 충분히 해결되는 사례도 기록합니다.
- 인터뷰 녹음은 사전 동의를 받고, 공유 기록은 필요한 범위에서 익명화합니다.

### 교수님 피드백 처리

피드백마다 **해석한 내용 / 반영 여부 / 반영 방법 또는 보류 이유 / 담당자**를 남깁니다. 의미가 불명확하면 임의로 기능을 추가하기 전에 확인합니다.

## 8. 기능 범위와 의사결정

### 새 기능을 추가할 때 확인할 질문

1. 누구의 어떤 문제를 해결하는가?
2. 인터뷰나 자료에서 필요성이 확인됐는가?
3. 현재 핵심 흐름에 반드시 필요한가?
4. 구현·검증·유지에 얼마나 작업이 필요한가?
5. 추가하려면 무엇을 미루거나 줄여야 하는가?

추가 제안은 즉시 개발하지 않고 우선순위 목록에 남깁니다.

### 결정 기준

**사용자 가치 → 수업 목표·평가와의 연결 → 구현·검증 가능성 → 일정·운영 부담**

쉽게 되돌릴 수 있는 세부 구현은 담당자가 합의된 기준 안에서 결정합니다. 사용자 흐름·데이터 구조·공통 기술·마감에 영향을 주는 변경은 관련 팀원과 논의합니다.

의견이 갈리면 선택지와 장단점을 기록하고, 가능하면 작은 실험으로 판단합니다.

## 9. 개발 협업 기본 규칙

기술 스택·폴더 구조·상세 코딩 규칙은 주제 선정 후 별도 문서로 확정합니다.

### GitHub 사용 제안

- `main`은 팀이 함께 사용하는 동작 가능한 상태로 유지합니다.
- 작업별 브랜치를 만들고 Pull Request(PR)로 변경을 검토합니다.
- 하나의 PR에는 가능한 한 하나의 목적을 담습니다.
- PR에는 **변경 이유 / 변경 내용 / 확인 방법 / 남은 문제**를 적습니다.
- 공통 구조·DB·API 변경은 관련 담당자와 먼저 공유합니다.
- 검토자가 이해하기 어려운 큰 변경은 나누거나 함께 설명합니다.

브랜치명 예: `feat/12-housing-form`, `fix/27-budget-total`

커밋 메시지는 변경 목적이 드러나게 작성합니다.

예: `feat: 주거 후보 입력 검증 추가`

### 검토 원칙

- 초반에는 함께 화면을 보며 검토하는 방식도 허용합니다.
- 검토자는 가능한 사람이 분담하고, 중요한 설계·계산 변경은 관련 이해가 있는 사람이 확인합니다.
- 작성자는 검토 결과를 반영하거나 반영하지 않은 이유를 설명합니다.
- 이해하지 못한 변경을 형식적으로 승인하지 않습니다.

## 10. 완료 기준과 AI 활용

### 개발 작업 완료 기준

- 합의한 완료 조건을 충족합니다.
- 관련 기능과 연결했을 때 동작합니다.
- 정상 입력뿐 아니라 빈 값·잘못된 값 등 주요 예외를 확인합니다.
- 계산·조건 분기 등 오류 영향이 큰 부분은 검증 사례를 남깁니다.
- 변경된 API·사용 방법·주의 사항이 있으면 문서를 갱신합니다.
- 검토를 완료하고, 남은 문제는 별도 작업으로 기록합니다.

‘코드를 작성했다’와 ‘사용할 수 있는 기능을 완성했다’를 구분합니다.

### AI 활용 원칙

- 아이디어 정리, 개념 학습, 코드 초안, 오류 분석 등에 활용할 수 있습니다.
- 제출하는 코드와 문서는 담당자가 이해하고 검증합니다.
- AI가 제시한 통계·출처·정책·계산 결과는 원자료와 대조합니다.
- 주요 설계나 핵심 계산에 AI를 활용했다면 검토 과정에서 공유합니다.
- API 키·비밀번호·사용자의 민감한 정보는 입력하거나 저장소에 올리지 않습니다.
- 강의의 별도 AI 활용 지침이 있다면 따릅니다.

## 11. 기여 기록과 회고

기여는 코드 양이나 커밋 수만으로 판단하지 않습니다.

**문제 조사, 인터뷰, 기획, 설계, 구현, 테스트, 검토, 문서화, 발표, 팀원 지원**을 작업과 결과물로 남깁니다.

주간 회의에서 다음을 짧게 확인합니다.

- 이번 주 완료한 일과 배운 점
- 도움이 필요했던 부분
- 특정 팀원에게 몰린 작업
- 다음 주 바꿀 협업 방식

기여나 참여 문제가 반복되면 구체적인 작업·일정 기록을 바탕으로 먼저 대화합니다. 팀 안에서 해결하기 어렵거나 수업 수행에 영향을 주면 교수님께 상황과 조정 시도를 설명하고 도움을 요청합니다.
